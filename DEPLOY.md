# Запуск SoyleUp на сервере — пошаговая инструкция

Рассчитано на то, что вы никогда раньше не арендовали сервер. Все команды —
скопировать и вставить в терминал. Если что-то не получается на каком-то
шаге — остановитесь и разберёмся, дальше двигаться не обязательно быстро.

Понадобится: доменное имя, VPS (виртуальный сервер) с доступом по SSH,
банковская карта для оплаты хостинга и домена, около 1–2 часов свободного
времени на первый запуск.

---

## Шаг 1. Домен

Купите домен у любого регистратора (например, через ps.kz, hoster.kz — для
зоны `.kz`, либо через любой международный регистратор для `.com`/`.io` и
т.п.). Домен и хостинг можно покупать у разных компаний — это нормально.

Запишите домен, он понадобится дальше, например `soyleup.kz`.

## Шаг 2. Аренда сервера (VPS)

Нужен сервер с дата-центром в Казахстане (важно для скорости и требований к
персональным данным). На момент написания такие услуги предлагают, например,
**ps.kz**, **hoster.kz**, **Yandex Cloud** (регион Казахстан) — сравните
текущие цены и тарифы сами на их сайтах, я их не привожу, чтобы не устарели.

Рекомендуемые характеристики для старта (беты на 20–50 учеников — на сервере
одновременно крутится API, сайт, база данных, очередь и хранилище файлов):

- 2 vCPU, 4 ГБ RAM, 60–80 ГБ SSD
- ОС: **Ubuntu 24.04 LTS** (или 22.04, если 24.04 недоступна)

После оплаты провайдер пришлёт вам **IP-адрес сервера** и **пароль root**
(или доступ по SSH-ключу — зависит от провайдера) на почту.

## Шаг 3. Первое подключение к серверу

На Mac/Linux — из обычного терминала, на Windows — через PowerShell или
[PuTTY]:

```bash
ssh root@<IP_сервера>
```

Введите пароль, который прислал провайдер (при вводе пароль не отображается
на экране — это нормально).

Создайте отдельного пользователя вместо работы под root (root — это
«суперпользователь», под ним лучше не работать постоянно):

```bash
adduser deploy          # придумайте пароль на вопрос "New password"
usermod -aG sudo deploy # даёт deploy право выполнять команды от имени root через sudo
```

Дальше подключайтесь уже под этим пользователем:

```bash
ssh deploy@<IP_сервера>
```

## Шаг 4. Firewall (базовая защита)

Разрешаем только то, что реально нужно: SSH, обычный веб (80) и HTTPS (443).

```bash
sudo apt update
sudo apt install -y ufw
sudo ufw allow 22
sudo ufw allow 80
sudo ufw allow 443
sudo ufw enable   # подтвердите "y"
```

## Шаг 5. Установка Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker deploy
```

Выйдите и зайдите заново (`exit`, потом снова `ssh deploy@<IP_сервера>`), чтобы
права применились. Проверьте:

```bash
docker --version
docker compose version
```

## Шаг 6. DNS — привязка домена к серверу

В панели управления вашего регистратора домена (там же, где покупали домен)
откройте настройки DNS и добавьте две A-записи, указывающие на IP сервера:

| Тип | Имя (хост)  | Значение          |
|-----|-------------|--------------------|
| A   | `@` (или пусто, «корень домена») | `<IP_сервера>` |
| A   | `storage`   | `<IP_сервера>` |

`storage.<ваш домен>` — отдельный адрес для хранилища файлов (записи речи,
картинки уроков), его тоже нужно направить на сервер.

Изменения DNS применяются не мгновенно — от нескольких минут до пары часов.
Проверить можно так (должен вернуться IP вашего сервера):

```bash
dig +short <ваш домен>
dig +short storage.<ваш домен>
```

Дальше не двигайтесь, пока оба адреса не начнут показывать IP сервера — без
этого Caddy не сможет выпустить сертификат HTTPS.

## Шаг 7. Скачивание проекта и настройка .env

```bash
git clone https://github.com/Nurbolat123/soyleup.git soyleup
cd soyleup
```

Настройки для Caddy и MinIO (файл `.env` рядом с `docker-compose.prod.yml`):

```bash
cp .env.prod.example .env
nano .env
```

Впишите:
- `DOMAIN=` ваш домен без `https://`, например `soyleup.kz`
- `ACME_EMAIL=` ваш email (на него Let's Encrypt пришлёт письмо, если
  сертификат вдруг не сможет обновиться)
- `S3_SECRET_KEY=` замените на случайную строку, например результат команды
  `openssl rand -hex 24`

Сохраните: `Ctrl+O`, `Enter`, выйти — `Ctrl+X`.

Настройки самого API (файл `apps/api/.env`):

```bash
cp apps/api/.env.example apps/api/.env
nano apps/api/.env
```

Обязательно поменяйте:
- `JWT_ACCESS_SECRET=` — случайная строка от 32 символов: `openssl rand -hex 32`
- `WEB_ORIGIN=https://<ваш домен>`
- `SEED_ADMIN_EMAIL=` и `SEED_ADMIN_PASSWORD=` — ваш реальный вход в админку
  (пароль минимум 12 символов, не используйте пример из файла)
- `S3_ACCESS_KEY=` и `S3_SECRET_KEY=` — **должны совпадать** с тем, что вы
  вписали в корневой `.env` на предыдущем шаге
- `S3_ENDPOINT=https://storage.<ваш домен>`
- `S3_PUBLIC_URL_BASE=https://storage.<ваш домен>/content`

`DATABASE_URL` и `REDIS_URL` можно не трогать — docker compose сам подставит
правильные адреса контейнеров при запуске.

Остальное (SMTP, Telegram-бот, алерты об ошибках) можно заполнить позже —
без них платформа тоже запустится, просто соответствующий канал уведомлений
будет выключен (это уже проверено на этапе разработки — приложение не падает
без них).

## Шаг 8. Первый запуск

```bash
docker compose -f docker-compose.prod.yml up -d --build
```

Первый раз сборка займёт несколько минут. Смотреть, что происходит:

```bash
docker compose -f docker-compose.prod.yml logs -f
```

(`Ctrl+C` — просто перестать смотреть логи, контейнеры продолжат работать).

Проверка:

```bash
curl https://<ваш домен>/api/v1/health
```

Должно вернуться `{"status":"ok"}`. Если вместо этого ошибка сертификата —
подождите ещё немного (Caddy выпускает сертификат при первом обращении,
может занять до минуты) и попробуйте снова.

Откройте `https://<ваш домен>` в браузере — должна открыться главная
страница с замочком (HTTPS) в адресной строке.

## Шаг 9. Создание администратора

```bash
docker compose -f docker-compose.prod.yml exec api npm run db:seed:prod
```

Войдите на `https://<ваш домен>/login` с email/паролем из `SEED_ADMIN_EMAIL`
/ `SEED_ADMIN_PASSWORD`, которые вы вписали в `apps/api/.env` на шаге 7.

Дальше через админку (`/admin/content`) загрузите настоящие курсы, уроки,
словарь и банк вопросов теста — **демо-контент на боевом сервере не
запускайте**, `db:seed:demo` — только для разработки.

## Шаг 10. Бэкапы

```bash
crontab -e
```

Добавьте две строки (замените `/home/deploy/soyleup` на реальный путь, если
клонировали в другое место — узнать его: `pwd`, находясь в папке проекта):

```cron
0 4 * * * cd /home/deploy/soyleup && ./scripts/backup.sh >> /var/log/soyleup-backup.log 2>&1
0 5 * * 0 cd /home/deploy/soyleup && ./scripts/restore-verify.sh >> /var/log/soyleup-restore-verify.log 2>&1
```

Первая строка — бэкап базы и файлов каждый день в 04:00. Вторая — проверка,
что бэкап реально восстанавливается, каждое воскресенье в 05:00.

Сразу же проверьте бэкап вручную, не дожидаясь ночи:

```bash
./scripts/backup.sh
./scripts/restore-verify.sh
```

В конце должно быть написано `OK: бэкап восстанавливается, данные на месте.`

## Шаг 11. Мониторинг ошибок

**Алерты в Telegram** (если у вас уже настроен Telegram-бот уведомлений —
см. `apps/api/.env.example`, поле `TELEGRAM_BOT_TOKEN`): напишите боту любое
сообщение, затем откройте в браузере
`https://api.telegram.org/bot<ваш токен>/getUpdates` и найдите там
`"chat":{"id":...}` — это число впишите в `apps/api/.env` как
`ALERT_TELEGRAM_CHAT_ID`, затем перезапустите API:

```bash
docker compose -f docker-compose.prod.yml up -d api
```

Теперь при падении сервера (ошибка 5xx) вам придёт сообщение в Telegram.

**Внешний мониторинг доступности** (рекомендую — так вы узнаете о падении,
даже если сам сервер не может отправить алерт): зарегистрируйтесь на
бесплатном сервисе вроде UptimeRobot или healthchecks.io и добавьте монитор
HTTP(S), который каждые несколько минут проверяет
`https://<ваш домен>/api/v1/health` — эти сервисы присылают email/Telegram,
если адрес перестаёт отвечать.

## Обновление платформы в будущем

Когда будут новые версии (новый код после `git push` в основную ветку):

```bash
cd /home/deploy/soyleup
git pull
docker compose -f docker-compose.prod.yml up -d --build
```

Миграции базы данных применяются автоматически при каждом старте `api`
(это уже встроено в образ), отдельно ничего запускать не нужно.

## Чек-лист перед бета-тестом на 20–50 учениках

- [ ] Домен открывается по `https://`, в браузере замочек без предупреждений
- [ ] `storage.<домен>` тоже открывается по HTTPS
- [ ] `./scripts/restore-verify.sh` хотя бы раз прошёл успешно
- [ ] `crontab -l` показывает обе строки из Шага 10
- [ ] `/privacy` и `/terms` проверены юристом — это больше не черновик с
      квадратными скобками
- [ ] Пароль администратора — настоящий сложный, не тестовый
- [ ] Настроен хотя бы один канал уведомлений (email или Telegram-бот) —
      иначе ученики и родители не получат напоминания и отчёты
- [ ] `ALERT_TELEGRAM_CHAT_ID` настроен — вы узнаете о падении сразу
- [ ] Внешний uptime-монитор подключён (Шаг 11)
- [ ] Загружен настоящий учебный контент через `/admin/content`, демо-данные
      не используются
- [ ] 2–3 тестовых человека прошли полный цикл без ошибок: регистрация →
      согласие родителя (если несовершеннолетний) → placement test → урок →
      домашнее задание → проверка куратором → отчёт родителю
- [ ] `.env` и `apps/api/.env` не попали в git (`git status` должен их не
      показывать — они в `.gitignore`)
